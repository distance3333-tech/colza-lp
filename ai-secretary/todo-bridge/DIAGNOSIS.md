# AI秘書 TODOリスト連携 障害調査

調査日: 2026-08-17

---

## 0. 先に結論

- **TODOリストの取得部分は Google Apps Script のウェブアプリ（Google Tasks 直叩き）でした。** コードは特定済みです。
- **買い物リストと「同じ仕組み」ではありません。** ここが今回の分かれ目です。TODOリストだけが Google Tasks 経由で、買い物リストは別経路です。だから片方だけ壊れます。
- **エラーは実際に握りつぶされていました。** `doPost` の `catch` が例外を JSON に詰めて **HTTP 200** で返し、しかも **ログを一切書いていません**。そのため Apps Script の実行ログ上は「完了（成功）」に見え、何が起きたか追えない状態でした。これは修正版で直しました。
- 真の failing 原因（権限か、リスト名の不一致か、デプロイのずれか）は、**私からは実行ログにも .env にもデプロイURLにも到達できないため確定できていません。** 確定させるための1手を §5 に用意しました。

## 2. なぜ買い物リストは生きているのか

ご認識のとおり**別データソース**です。ToDo版スクリプトは Google Tasks（`tasks.googleapis.com`）だけを見ており、買い物リストはこの経路を通っていません。

つまり「同じ仕組みのはずなのに片方だけ壊れた」のではなく、**もともと別系統で、Google Tasks 系統だけが落ちている**という状態です。切り分けの軸としては、

- 買い物リストが動く = 秘書本体・`.env` の合言葉・ネットワークは生きている
- ToDoだけ落ちる = **Google Tasks の認可か、リスト名か、ToDo用デプロイURL** のいずれか

の3つに絞り込めます。カレンダー/Gmail 版は別プロジェクト・別スコープなので、そちらが動いていても ToDo 版の認可状態の証拠にはなりません。

## 3. エラーが見えなくなっていた原因（ご依頼 4番）

**握りつぶしは実在しました。** 元コードの該当箇所:

```js
} catch (err) {
  return json({ error: String(err) });   // ← ログに何も残さず、HTTP 200 で返す
}
```

問題は3つあります。

1. **ログに書いていない。** `console.error` も `Logger.log` も無いので、Apps Script の「実行数」画面では**ステータスが「完了」**になります。失敗が失敗として記録されていませんでした。
2. **HTTP 200 で返す。** 秘書側が HTTP ステータスだけ見ていると成功扱いになり、`items` が無いことだけで「見に行けませんでした」に落ちます。
3. **`getItems` が `null` を返す経路が無言。** リスト名が一致しないと `findList` が `null` を返し、`getItems` も `null` を返して、**例外すら発生しません**。この場合 `{"items": null}` が 200 で返るだけで、`error` フィールドすら付きません。エラーメッセージが「権限か一時的なエラー」としか言えなかったのは、まさにこの経路の可能性が高いです。

なお `api()` 自体は `Tasks API 403: {...}` のように**ステータスと本文を持った例外を投げており、情報源としては十分でした**。その情報が `catch` で JSON に詰められたきり、どこにも記録されずに消えていた、という構図です。

## 4. 直したこと（`コード.gs`）

`コード.gs` が置き換え版です。**レスポンスの形は後方互換**（`items` / `added` / `completed` はそのまま、`ok` などを追加しただけ）なので、秘書側のコードを変えずに差し替えられます。

- `catch` で `console.error` に **action / list / message / HTTPステータス / 応答本文 / スタック** を全部出す。→ 実行ログに残り、実行が「失敗」として記録される。
- `api()` の例外に `httpStatus` と `httpBody` を持たせ、本文の切り詰めをやめた。
- **リスト名の不一致を専用エラーにした。** `list_not_found` を返し、**実在するリスト名の一覧を一緒に返す**。名前がずれていれば一目で分かります。
- `complete` で「リストが無い」と「項目が無い」を区別。
- 全レスポンスに `ok: true/false` を追加。
- `completeItem` の潜在バグを修正（題名が空の項目が混ざると `t.title.indexOf` で落ちる）。
- `findList` が部分一致で解決したときログに残す（意図しないリストを掴んでいないか確認できる）。
- **`diagnose()` を追加**（§5-A）。
- **`checkListName(name)` を追加**（§5-B）。

> 差し替え時、`SECRET` はプレースホルダにしてあります。**元のスクリプトの値をコピーして貼ってください。**（このリポジトリは公開のため、実値は入れていません。）

## 5. 原因を確定させる手順

上から順に。ほぼ A か B で判明します。

### A. まず `diagnose()` を実行する ← これが本命

1. ToDo版スクリプト（§1 の1行目のリンク）を開く
2. `コード.gs` の中身を本ファイルの修正版に差し替え、`SECRET` を元の値に戻す
3. 関数リストから **`diagnose`** を選んで実行
4. 実行ログを読む

読みどころは2つです。

- **`tokeninfo` の `scope`** … ここに `https://www.googleapis.com/auth/tasks` が**無ければ権限不足で確定**です。`expires_in` も出るので、トークンの有効期限もここで分かります（数千秒あれば正常。トークン自体は毎回発行されるので「期限切れ」より**そもそも scope が付いていない**方が疑わしい）。
- **リスト名の一覧** … 実在する Google ToDo のリスト名がそのまま出ます。

`diagnose()` が `Tasks API 403 ... insufficient authentication scopes` で落ちた場合 → **承認のやり直し**（§6-①）。

### B. リスト名を突き合わせる

`diagnose()` が出したリスト名と、**秘書が `list` に渡している文字列**を比べます。秘書側で `list: 'ToDoリスト'` のように投げていて、実際の Google ToDo 側が「マイタスク」「仕事」などだった場合、`findList` は `null` を返し、**例外なしで静かに失敗**します（§3-3）。これが今回の症状（権限エラーらしきメッセージなのに実は名前ずれ）の最有力候補です。

エディタから `checkListName('秘書が渡している名前')` を実行すれば、その名前がどのリストに解決されるか／しないかを直接確認できます。

修正は**どちらか片方**でOK:
- Google ToDo 側のリスト名を秘書の期待どおりに改名する
- 秘書側が渡す `list` を実在名に合わせる（あるいは `list` を渡さず既定リストを使う）

### C. デプロイURLの確認

`.env` の ToDo 用URLが、**ToDo版プロジェクトの現行デプロイ**を指しているか確認してください。特に §1 の**空プロジェクト**を指していないか。

あわせて、**コードを直したら「新しいデプロイ」を作り直すこと**。「デプロイを管理」で既存デプロイを更新しない限り、公開URLは**古いコードのまま**です。08/09 21:28 作成 → 21:37 更新という履歴があるので、*更新後に再デプロイしていない*可能性は十分あります。

### D. 秘書側のエラーハンドリング

秘書本体（`.env` を読んでいる側。今回のリポジトリからは到達できませんでした）では、レスポンスの `error` / `httpStatus` / `httpBody` / `available` を**そのままログに出す**ようにしてください。修正版はこれらを返します。HTTPステータスだけ見て成功判定していると、今回と同じ見えなさが再発します。

## 6. 想定される直し方

**① 権限不足だった場合（`scope` に tasks が無い / 403）**

1. ToDo版スクリプトで `appsscript.json` の `oauthScopes` に `https://www.googleapis.com/auth/tasks` があることを確認
2. https://myaccount.google.com/permissions で該当スクリプトのアクセス権を**いったん削除**
3. エディタで `diagnose` を実行 → 承認画面が出るので**改めて許可**
4. **新しいデプロイを作成**（承認し直しただけでは既存デプロイに反映されないことがある）
5. LINE から「TODOリストお願い」

**② リスト名の不一致だった場合** → §5-B のどちらかを揃える。再デプロイ不要（秘書側を直す場合）。

**③ デプロイURLのずれだった場合** → `.env` のURLを現行デプロイのものに差し替える。

## 7. できなかったこと

正直に書きます。次の3つには私の権限が届かず、**原因の断定には至っていません**。

- **Apps Script の実行ログ／エラーログ（ご依頼 3番）を読めませんでした。** Apps Script API も Cloud Logging も、このセッションからは参照できません。加えて §3 のとおり、そもそも**失敗時にログが書かれていなかった**ので、過去分は遡っても記録が残っていない可能性が高いです。まず修正版を入れて、次の失敗を捕まえるのが最短です。
- **OAuth の認可状態・トークンの有効期限（ご依頼 2番）を直接確認できませんでした。** Google Tasks のコネクタが無く、`myaccount.google.com/permissions` も参照できません。代わりに、同じことを自分で確認できる `diagnose()` を用意しました。
- **秘書本体のコードと `.env` を確認できませんでした。** 「ToDoリストを見に行けませんでした」という文字列は、リポジトリにもドライブにも存在しません。ローカルPC側にあると思われます。そのため、秘書が `list` に何を渡しているか（§5-B の突き合わせ）は、お手元での確認をお願いします。

修正版の差し替えと `diagnose()` の実行ログを共有いただければ、そこから先は確定できます。
